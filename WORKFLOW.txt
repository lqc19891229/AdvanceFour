《前进四 / ADVANCE FOUR》开发工作流

========================================
总原则
========================================

项目开发统一遵循：

设计先确认
→ 数据先定义
→ 最小功能实现
→ 独立测试
→ 集成验证
→ 文档同步
→ 打版本

数据系统统一遵循：

Excel 是源数据
→ JSON 是中间数据
→ .tres 是生成数据
→ 游戏只读取生成数据

项目目录统一遵循：

按功能分类，不按文件类型堆放。


========================================
数据工作流
========================================

1. 修改源数据

源文件：
res://tools/data_import/source

所有策划数值优先在 Excel 中修改。

禁止把 data/generated/ 下的 .tres 当作源数据手动维护。

2. 验证数据

修改 Excel 后先执行：

验证内容包括：
- ID 是否为空
- ID 是否重复
- ID 命名是否合法
- 尺寸是否合法
- 数值是否合法
- Sheet 对应的专属参数是否完整

验证失败时：

停止导入
→ 修改 Excel
→ 重新验证

不允许带错误数据继续生成。


3. 导入数据

验证通过后执行：

前进四：导入模块数据

流程：

game_data.xlsx
→ Python 导入器
→ tools/data_import/cache/modules.json
→ Godot EditorPlugin
→ data/generated/modules/*.tres
→ data/generated/module_database.tres


4. 生成数据规则

以下目录为生成数据：

res://data/generated/

原则：
- 不手动修改生成的 .tres
- 不手动维护 module_database.tres
- 需要修改参数时回到 Excel
- 重新导入后允许覆盖旧生成数据


========================================
功能开发工作流
========================================

每个新系统推荐按以下顺序开发：

1. 数据
2. 逻辑
3. 显示
4. UI

例如战斗飞船：

数据：
ShipData / ModuleInstance / ModuleDefinition

逻辑：
移动 / 能源 / 武器 / 损伤

显示：
Ship Scene / Module View

UI：
战斗 HUD / 状态面板

先保证规则能运行，再制作正式表现。


========================================
需求确认工作流
========================================

在实现较大的新功能前，先确认：

- 这个系统解决什么问题
- 玩家如何使用
- 核心规则是什么
- 需要哪些数据
- 与现有系统有什么关系
- 哪些内容本阶段暂时不做

需求确认后再开始修改代码和场景。

避免边实现边不断改变最底层规则。


========================================
场景与脚本管理
========================================

脚本原则：

一个脚本有一个主要职责。

Prototype 阶段允许适度合并逻辑，避免过度拆分。

当脚本明显包含多个独立系统，或者体积过大时再拆分。

命名规范：

场景：
snake_case.tscn

脚本：
snake_case.gd

Resource 类：
PascalCase

Resource 脚本文件：
snake_case.gd

数据 ID：
lower_snake_case

例如：
reactor_small_01
engine_main_01
weapon_cannon_01
armor_light_01
bridge_basic_01

显示名称可以修改，已经使用的 ID 尽量不要修改。


========================================
README 文档规范
========================================

主要系统目录应包含 README.txt。

README 推荐结构：

一、用途
说明目录负责什么。

二、主要文件
列出重要脚本、场景、Resource 及作用。

三、使用方式
说明系统如何使用。

四、依赖
说明依赖哪些系统。

五、注意事项
说明不能手动修改的文件、特殊规则等。

需要更新 README 的情况：
- 新增重要脚本或场景
- 删除重要脚本或场景
- 修改目录结构
- 修改系统使用方式
- 修改系统核心职责

不要求更新 README 的情况：
- 普通 Bug 修复
- 单纯调整数值
- 不影响使用方式的小改动


========================================
测试工作流
========================================

后续推荐建立：

res://dev/

专门存放开发测试场景，例如：
- module_test.tscn
- ship_movement_test.tscn
- weapon_test.tscn
- enemy_test.tscn

测试场景不属于正式游戏流程。

开发独立系统时优先直接运行对应测试场景，减少重复进入完整游戏流程的时间。


========================================
Bug 修复工作流
========================================

发现 Bug 后：

复现问题
→ 判断数据问题 / 逻辑问题 / UI问题
→ 定位原因
→ 修复
→ 验证原问题
→ 回归验证相关旧功能
→ 必要时更新文档
→ 打新版本

不要只修改报错行后立即发布。

已经确定的重要规则要作为回归检查项保留。

例如当前飞船编辑器：
- 模块可以分开放置
- 模块不能重叠
- 编辑阶段允许能量不足
- 可用设计要求总耗能 <= 总供能
- 核心模块用于沉没判定


========================================
版本工作流
========================================

Prototype 阶段继续使用：

v0.10
v0.11
v0.12
...

小版本用于：
- 新增小功能
- 数据结构调整
- Bug 修复
- UI 调整
- 工具调整

进入完整开发阶段后再使用：
- Prototype
- Vertical Slice
- Alpha
- Beta
- Release Candidate


========================================
版本发布检查
========================================

每次生成新的项目前检查：

[ ] Godot 项目可以正常打开
[ ] 主场景可以运行
[ ] 没有明显脚本错误
[ ] Excel 数据验证通过
[ ] Excel 导入流程可用
[ ] JSON cache 可以生成
[ ] .tres 可以生成和加载
[ ] ModuleDatabase 可以正常加载
[ ] 重要旧功能没有被破坏
[ ] README 已按需要更新
[ ] WORKFLOW.txt 仍然存在
[ ] PROJECT_STRUCTURE.txt 已与目录同步
[ ] 没有废弃旧目录或重复文件

以后使用 Git 后增加：

[ ] git status 已检查
[ ] 正式版本已 commit


========================================
沟通与实现流程
========================================

后续较大的功能推荐统一采用：

提出需求
↓
先讨论方案
↓
确认数据结构与规则
↓
确认目录和文件变化
↓
开始实现
↓
生成新版本
↓
实际测试
↓
反馈问题
↓
修正并进入下一阶段

对于已经明确的小 Bug，可以直接修复，不必重复完整方案确认。


========================================
工作流核心句
========================================

设计先确认，数据先定义，功能做最小闭环。

Excel 是源数据，生成文件不手改。

系统按功能组织，重要目录有说明。
