========================================
一、核心分层
========================================

项目当前按四层理解：

1. 策划数据层
   game_data.xlsx
   ↓
   Python
   ↓
   modules.json
   ↓
   Godot importer
   ↓
   .tres / ModuleDatabase

2. 飞船设计数据层
   ShipData
   ├─ Hull Layout
   │  └─ ShipHullCell
   └─ Equipment
      └─ ShipModuleInstance

3. Runtime 战斗实体层
   ShipRuntime
   ├─ HullCellRuntime
   ├─ WeaponRuntime
   ├─ ProjectileRuntime
   ├─ PlayerShipController / AIShipController
   └─ Appearance Layer

4. 关卡战斗层
   BattleDefinition
   ↓
   battle.tscn / Battle
   ↓
   生成玩家与敌舰、调度波次、判定胜负、结算

飞船编辑器只负责设计飞船与发起出航，不承担正式关卡战斗规则。


========================================
二、正式战斗场景原则
========================================

1. res://game/combat/battle.tscn 是正式战斗容器。
2. 后续普通关卡、精英战、Boss 战默认全部复用 battle.tscn。
3. 不因为增加新关卡而复制 battle.tscn。
4. 不在 battle.gd 中持续堆叠“第几关”的专用 if / match。
5. 不同关卡通过 BattleDefinition Resource 提供配置。
6. 当前第一份正式配置为：
   res://game/combat/definitions/stage_001.tres
7. 上层系统通过 SceneTree meta：
   battle_definition_path
   指定下一场 BattleDefinition，然后统一进入 battle.tscn。
8. 若没有提供外部配置，battle.tscn 使用自身绑定的 stage_001.tres。
9. 重新挑战时必须继续使用当前 BattleDefinition。
10. BattleDefinition 当前管理：
    - battle_id
    - display_name
    - wave_enemy_counts
    - preparation_seconds
    - intermission_seconds
    - spawn_interval_seconds
    - spawn_radius
    - return_scene_path
    - restore_saved_ship_on_return
11. 敌舰蓝图 / 波次敌舰组合 / Boss / 奖励目前尚未进入 BattleDefinition；后续应继续数据化，不写死进 battle.gd。


========================================
三、Hull 与 Equipment 数据规则
========================================

1. Hull Layout 与 Equipment 是两层独立数据。
2. ShipHullCell 保存：
   - grid_position
   - hull_type
   - max_hp
   - current_hp
   - mass
3. 第一版 basic_hull：
   - max_hp = 20
   - mass = 2
4. Equipment 必须完整覆盖已有 Hull Cell。
5. Hull 当前允许：
   - 不相邻
   - 不连通
   - 中间空格
6. Hull Cell 上有 Equipment 时不能直接拆除该 Hull Cell。
7. ShipHullCell.mass 当前保留为结构数据，不参与移动计算。
8. Equipment Definition 已取消共通 hp 与 mass。
9. Energy / Propulsion / Weapon / Function / Core 不拥有独立 hp。
10. Defense 单独保留 hp 与 protection。
11. 多格 Equipment 的运行效率取覆盖 Hull Cell 健康比例平均值。
12. 核心覆盖的 Hull Cell 全部损毁时，整船判定沉没。


========================================
四、区域耐久与伤害规则
========================================

1. 战斗碰撞基础单位是 Hull Cell，不是整个 Equipment 外框。
2. 区域最大 HP =
   ShipHullCell.max_hp + 覆盖该格的 Defense hp 分配值。
3. 多格 Defense.hp 平均分配到它覆盖的 Hull Cell。
4. 区域 current HP 最终映射回 ShipHullCell.current_hp。
5. Defense.protection 是百分比减伤，不是额外独立运行时血条。
6. Projectile 使用本物理帧整段 swept ray 处理高速命中。
7. 当前伤害支持 HP-overkill 穿透：
   前方 Hull 区域被击穿并仍有剩余伤害时，继续沿弹道查询后方区域。
8. 发射者被摧毁后，已经生成的 Projectile 继续独立存在与造成伤害。
9. 当前没有：
   - 独立穿甲系数
   - 材质抗性
   - 爆炸 / 溅射
   - 正式伤害类型


========================================
五、武器规则
========================================

Weapon 数据当前由 Excel 正式提供：
- firepower
- attack_range
- fire_interval
- turn_speed_degrees
- projectile_speed
- firing_arc_degrees
- fire_angle_tolerance_degrees
- texture_path
- turret_texture_path

规则：
1. rotation_quarters 定义武器安装方向，也是射界中心基准。
2. WeaponRuntime 独立旋转炮塔。
3. 自动选敌、炮塔转向和开火都受 firing_arc_degrees 约束。
4. attack_range 同时限制选敌距离与弹丸最大飞行距离。
5. Projectile 在开火时记录本发自己的射程和速度。
6. WeaponRuntime 的 operational 与 powered 分离。
7. 武器对应结构失效后不可恢复工作；单纯恢复供能不会复活已失效武器。


========================================
六、能源与推进规则
========================================

1. RuntimeShip 记录 module_powered_by_uid。
2. 供能不足时使用当前 Prototype 固定优先级：
   核心 > 能源 > 动力 > 防护 > 功能 > 武器
3. 同类型按 module.uid 升序稳定分配。
4. is_energy_sufficient() 只表示能否覆盖全部存活负载。
5. 供能不足不代表所有模块都停止工作。
6. 推进只统计当前仍有效且已供电的 Propulsion。
7. 当前运动模型不计算 Hull / Equipment 质量。
8. 当前最高速度、加速度、松油减速度由有效推力乘各自 scale 决定。
9. 动力所在 Hull 受损会通过效率降低有效推力。


========================================
七、Appearance Layer
========================================

1. Appearance 只负责 Runtime 战斗显示，不修改 ShipData。
2. 编辑器继续完整显示 Hull + Equipment 工程视图。
3. 战斗中根据 Hull Layout 生成连续外壳。
4. Core / Weapon / Propulsion 外露。
5. Energy / Defense / Function 默认被船壳包覆。
6. 武器视觉拆为 base + turret，炮塔贴图跟随 WeaponRuntime 独立转动。
7. 后续舰首、舰尾、推进开孔、装甲蒙皮属于 Appearance 扩展，不应改变底层飞船数据结构。


========================================
八、存档与战斗状态
========================================

1. ShipSerializer 当前 FORMAT_VERSION = 2。
2. 存档保存 Hull Cell：
   - position
   - hull_type
   - max_hp
   - current_hp
   - mass
3. Equipment 保存：
   - module_id
   - position
   - rotation
4. 运行时 uid 不作为长期存档稳定标识。
5. 旧 v1 存档继续兼容读取。
6. 当前正式战斗仍从 user://ships/test_ship.json 读取玩家设计。
7. 同一场 battle 内战损跨波次保留。
8. 当前退出 / 重试仍重新从存档建立 RuntimeShip。
9. 下一阶段 v0.32 应建立正式战后状态写回：
   Runtime 战损
   → BattleResult / Run State
   → 战损持久化
   → 维修 / 奖励 / 下一战


========================================
九、编辑器职责
========================================

飞船编辑器负责：
- Hull 铺设 / 拆除
- Equipment 安装 / 移动 / 旋转
- 设计合法性
- 属性预览
- 保存 / 载入设计
- 发起正式战斗
- 发起独立 AI 开发测试

飞船编辑器不负责：
- 波次逻辑
- 战斗胜负
- 敌舰生成
- 关卡配置
- 奖励
- Boss 流程

点击“出航战斗”当前执行：
验证设计
→ 保存玩家设计
→ 指定 stage_001.tres
→ 切换到统一 battle.tscn。


========================================
十、测试与验证
========================================

统一验证入口：
python3 tools/verify_project.py --godot /path/to/godot

当前 Godot 版本：
4.6.1

战斗回归位于：
game/combat/dev/combat_regression_test.gd

至少覆盖：
- 玩家真实输入与移动反馈
- 波次与波间
- 胜利 / 失败
- 残留弹丸
- 同帧失败优先
- 阵营碰撞隔离
- 非法关卡配置
- 编辑器 → 正式战斗 → 重试 / 返回


========================================
十一、目录文档规则
========================================

1. 主要功能目录放 README.txt。
2. README 说明：
   - 目录职责
   - 主要文件
   - 使用方法
   - 依赖
   - 当前边界
3. 新增 / 删除重要文件、改变核心职责或使用方式时同步更新 README。
4. data/generated 禁止手动修改。
5. Excel 是模块策划数据唯一真源。
6. 中文 Excel 表头仅服务策划可读性；导入阶段转换为稳定英文内部字段。
