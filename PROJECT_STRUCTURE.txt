========================================
一、四个核心目录的边界
========================================

1. tools：生产与验证内容
   - 策划源表、缓存、导入脚本、验证工具。
   - 不保存 PNG / 音频等正式游戏素材，也不作为游戏 Runtime 的正式资源路径。

2. data：描述内容
   - 游戏运行时加载的数据结构、配置实例和正式素材。
   - definitions 是数据“类型/结构”；modules/enemies/battles 是具体实例。
   - assets 是 Runtime 正式素材。
   - 不再存在 generated 层级。
   - 自动生成文件直接归入对应业务目录。

3. game：执行内容
   - 场景、Node、Controller、Runtime、Renderer、Gameplay、UI、开发测试。
   - 不保存策划源数据、纯 Definition 类或正式 PNG 素材。

4. core：支撑整个项目
   - 跨场景、跨系统共享的底层服务。
   - 不放 Ship / Weapon / Battle 等具体玩法规则。

判断：
“它是什么？” → data
“它怎么运行？” → game
“它怎么被制作出来？” → tools
“所有系统都需要的底层能力？” → core

========================================
九、素材唯一来源规则
========================================

1. PNG、音频等游戏素材只保存在 data/assets。
2. tools 不再保存 art_source，也不维护与 data/assets 重复的素材副本。
3. game 与 data Resource 统一引用 data/assets。
4. 当前仓库内素材采用“单份正式文件”策略。
5. 未来若出现 PSD / Aseprite / Blender 等制作工程文件，再单独设计源码素材管理，不与 Runtime PNG 混为一谈。


========================================
十、v0.37 Run / 路线闭环
========================================

core/autoload/run_state.gd
- 当前 Run 的跨场景状态。
- current_ship：当前真实飞船状态。
- battle_entry_ship：当前战斗开场快照，用于 Retry。
- currency：当前 Credits。
- completed_battles：已完成战斗。
- last_result：最近一次已记录战斗结果。

data/definitions/combat/battle_result.gd
- 战斗结果数据：胜负、battle_id、战后 ShipData、奖励、击毁数、下一战路径。

正式流程：
Ship Editor
→ RunState.start_run_with_route()
→ stage_001
→ Victory
→ BattleResult
→ RunState.commit_victory()
→ Battle Result Screen
→ Route Map
→ Shop / Run Refit
→ Route Map
→ stage_002
→ Route End

Route：
- data/definitions/run/run_route_node_definition.gd：路线节点类型、目标资源、下一节点和星图位置。
- data/definitions/run/run_route_definition.gd：路线节点集合、起点与连接合法性。
- data/routes/prototype_route.tres：当前正式 Prototype 航线。
- game/run/route/：星图展示与节点选择。
- RunState 记录当前路线节点和已完成节点；正式 Run 通过路线决定战斗 / 商店 / 整备 / 终点。
- 当前路线：stage_001 → [Shop / Refit] → stage_002 → End。

Shop：
- data/definitions/run/shop_item_definition.gd：单个商品内容与 Credits 价格。
- data/definitions/run/shop_definition.gd：数据化商店商品表。
- data/shops/basic_shop.tres：当前 Prototype 固定补给商店。
- game/run/shop/：商店场景与购买 UI。
- RunState.purchase_shop_item()：原子扣 Credits 并写入 Run Inventory。
- v0.37.1 起每个商店节点固定 4 个商品槽；首次进入时按 combat / systems / utility / any 槽规则从商品池无重复生成。
- 生成结果和每槽 SOLD 状态由 RunState.shop_node_states 按路线节点保存；刷新/重新进入不会换货，购买后不补货。
- 最终关不显示商店。

Reward Choice：
- BattleDefinition.reward_choices：战后成长奖励候选。
- BattleRewardOption：一个候选可奖励模块和/或 Hull。
- Credits 与固定奖励在 Victory commit 时结算；reward_choices 必须额外选择 1 项。
- pending choice 会阻止 Refit / Next Battle / End Run，但不阻止维修。
- 每场候选只能领取一次。

Run Inventory：
- RunState.module_inventory：module_id → 数量。
- RunState.hull_stock：可新增 Hull Cell 数量。
- BattleDefinition / BattleResult 支持固定模块与 Hull 奖励。
- Run Refit 安装消耗库存，拆除返还库存，移动 / 旋转免费。
- 普通设计模式不受 Run Inventory 限制。

局部维修：
- RunState.get_repair_cost_for_cell(position)：按单格缺失 Hull HP 计算费用。
- RunState.repair_cell(position)：只维修选中 Hull Cell。
- Battle Result Screen：显示受损 Hull、覆盖 Equipment、当前效率与修复后预计效率。
- 当前规则：1 缺失 Hull HP = 1 Credit；资金不足时不改变 Credits 或 Hull HP。

规则：
- Victory：提交战损并发放奖励。
- Defeat：不提交战损，不发奖励。
- Retry：从 battle_entry_ship 重新开始。
- Run Refit：只修改 RunState.current_ship，不覆盖 user://ships/test_ship.json。


模块仓库（v0.38.0）
- RunState.module_inventory 继续作为模块仓库账本。
- 基础仓储容量：12。
- 模块仓储占用固定由 ShipModuleDefinition.get_storage_cost() = size.x × size.y 计算；旋转不改变占用。
- Hull Stock 独立保存，不计入模块仓储。
- FunctionModuleDefinition.storage_capacity > 0 的已安装模块会增加飞船仓储容量。
- 当前标准货舱 function_cargo_hold：2×2，+16 仓储，自身进入仓库时占 4。
- 商店模块购买、固定战斗模块奖励、成长模块奖励都必须先通过仓储容量检查。
- 整备拆下模块仍允许写回仓库；若因此形成超载，新的商店购买/模块奖励会被阻止，直到玩家重新安装或消耗模块。


Warehouse Screen（v0.39.0）
- game/run/warehouse/warehouse_screen.tscn：模块仓库管理场景。
- game/run/warehouse/warehouse_screen.gd：类型筛选、堆叠库存、容量/超载显示、模块详情与路线合法整备跳转。
- Route Map 增加“查看仓库”入口；进入/返回仓库本身不推进路线节点。
- “前往整备”只有当前路线允许 REFIT 时才可用；不会绕过路线选择。
- game_data.xlsx 的 Function Sheet 正式增加 storage_capacity；标准货舱由 Excel → JSON → .tres 正式数据链生成。
- data/assets/modules/function_cargo_hold.png：标准货舱正式模块贴图。


战利品临时区（v0.40.0）
- game/run/loot/loot_screen.tscn：战斗胜利后的模块战利品处理场景。
- BattleDefinition.reward_module_ids / reward_module_counts 当前作为固定模块掉落清单。
- commit_victory() 不再自动把固定模块奖励写入仓库。
- BattleResult 保存每件掉落的 loot_resolved / loot_taken 状态。
- RunState.take_loot()：仓储容量允许时将指定战利品写入 module_inventory。
- RunState.discard_loot()：放弃指定战利品，不改变仓库。
- 有未处理 Loot 时阻止路线选择与下一战。
- 当前为固定掉落清单；随机掉落池与权重属于后续版本。


随机掉落表（v0.41.0）
- data/definitions/combat/loot_table_entry.gd：单个候选模块、权重与数量范围。
- data/definitions/combat/loot_table_definition.gd：掉落数量、重复规则、候选池与加权抽取。
- data/loot_tables/stage_001_loot.tres / stage_002_loot.tres：当前两场战斗正式掉落池。
- BattleDefinition.loot_table：战斗引用掉落表；保留旧 reward_module_ids 作为兼容回退接口。
- Battle 在胜利时 roll() 一次，实际结果写入 BattleResult，进入 Loot Screen 后不再重新抽取。
- 固定 seed 的 roll(seed) 用于自动测试；正式战斗使用随机种子。
- 当前不设计装备稀有度；weight 仅表示掉落概率权重，不代表品质。


战斗配置包（v0.41.1）
- data/battles/<battle_id>/battle.tres：该场战斗的 BattleDefinition。
- data/battles/<battle_id>/loot.tres：该场战斗的 LootTableDefinition。
- BattleDefinition 直接引用同目录 loot.tres。
- 删除独立 data/loot_tables/ 目录。
- 普通战 / 精英战 / Boss 仍统一使用共享 battle.tscn + BattleDefinition + LootTableDefinition。
- “精英”首先作为数据强度差异表达：更强 battle.tres + 更高收益 loot.tres；除非未来 UI/规则明确需要，不新增 EliteBattle 专用运行时代码。


精英战（v0.42.0）
- data/battles/elite_001/battle.tres：精英战 BattleDefinition。
- data/battles/elite_001/loot.tres：精英战 LootTableDefinition。
- elite_001 仍是 RunRouteNodeDefinition.NodeType.BATTLE，不新增 ELITE_BATTLE。
- 精英强度完全由 battle.tres 表达：3 波共 12 艘敌舰、更短生成间隔、220 Credits。
- 精英收益完全由 loot.tres 表达：drop_count = 4、禁止重复，并提高机炮 / 动力 / 能源 / 标准货舱等高价值模块权重。
- Prototype Route：battle_001 后可选 shop_001 / refit_001 / elite_001，三条分支均汇合到 battle_002。


双资源经济（v0.43.0）
- RunState.energy_crystals：能量结晶，通用交易通货。
- RunState.parts：零件，工程维修 / 制造资源。
- BattleDefinition.reward_energy_crystals / reward_parts：每场战斗的数据化双资源奖励。
- BattleResult 保存本场实际双资源奖励，commit_victory() 一次性写入 RunState。
- ShopItemDefinition.price_energy_crystals：商店商品只以能量结晶定价。
- repair_cell() / repair_all()：当前只消耗零件，规则为 1 缺失 Hull HP = 1 零件。
- 能量结晶与零件的增减均由 RunState API 负责，UI 不直接修改资源。
- v0.43 不实现模块制造；空间站以零件制造模块属于 v0.44。
